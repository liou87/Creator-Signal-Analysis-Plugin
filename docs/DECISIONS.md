## 范围类

### D-00 平台选 B 站，指数选商业化程度

- **选项**：B 站 / YouTube / 小红书 / X；商业化程度 / 公开求助意愿 / 两个都做
- **选择**：B 站 + 商业化程度，只做一个指数
- **理由**：B 站空间页不登录即可访问，公开信息丰富。商业化程度的证据是客观的、能在页面上指给人看的（广告声明、购物链接、付费入口）；求助意愿依赖语义判断，更难辩护。做深一个比做浅两个更能讲清楚。
- **代价**：不覆盖需求里的另一个示例信号。

### D-01 分数给谁用

- **质疑**：没有使用者和决策场景，任何权重都无从辩护。
- **选项**：线索筛选 / 品牌方选达人 / 观众判断可信度 / 不绑定场景
- **选择**：线索筛选
- **理由**：需求举的两个例子（商业化程度、公开求助意愿）合起来是「有没有生意、有没有需求」，是线索评分的结构。**这是推断，不是需求明说的。**
- **影响**：所有变现方式都计入，包括创作者卖自己的周边和课程。
- **代价**：不区分合作品牌的品类，不适合直接拿去做品牌选达人。如果场景是「观众判断可信度」，分数的含义会完全不同（披露越规范反而越可信）。

## 评分类

### D-02 两层用加法合成

- **质疑**：强度和广度相加，同样 50 分可能是完全不同的两种人。
- **选项**：加法 / 几何平均 / 不合成只给两个分
- **选择**：加法，两个子分始终并列展示
- **理由**：变现渠道互为替代，应允许补偿。几何平均会把单渠道创作者压到接近 0。需求明确要「一个指数」，不合成有答非所问的风险。
- **代价**：单个数字有信息损失，靠分数拆解弥补。

### D-03 占比用收缩估计

- **质疑**：发 3 条视频有 2 条广告，占比 67%，直接满分？
- **选项**：原始占比 / 绝对条数 / 收缩估计
- **选择**：`r̂ = Σw / (n + 5)`
- **理由**：样本少时向 0 收缩。3 条 2 广告 → 0.25；30 条 10 广告 → 0.29。绝对条数则会惩罚更新慢的人。
- **代价**：多一个参数；低产创作者被系统性压低。

### D-04 取样窗口

- **质疑**：取最近 30 条，日更的人是一个月，月更的人是两年半。
- **选择**：最近 30 条且 12 个月内，报告写明覆盖时间段
- **代价**：低产者样本更少，由 D-03 和置信度兜底。

### D-05 封顶值来自样本分位数

- **质疑**：占比 0.5 即满分，这个 0.5 哪来的？
- **选择**：初值 0.5，校准后换成样本 r̂ 的 90 分位数
- **理由**：这是纯统计，不需要人工判断。参照新榜指数用基准常数做标准化的做法。
- **代价**：二十个样本的 90 分位数不稳定，如实说明。

### D-06 疑似档权重保留先验 0.5

- **质疑**：0.5 哪来的？
- **选项**：固定折扣 / 用标注集上的实测精确率
- **选择**：保留 0.5，不确定性由区间承担
- **理由**：理想做法是实测精确率（「判为疑似时真是商业内容的概率」）。但判断软广需要行业经验，本项目的标注者明确表示不具备。让非专业者硬标，得到的数字比先验更误导人。
- **代价**：点估计里仍有一个没有依据的数；区间可能较宽。
- **备注**：这是最初方案被推翻的地方。最初打算用实测精确率，讨论后改为现在的做法。

### D-07 账号层只分强弱两级

- **质疑**：10/10/5/5/5/5 凭什么？
- **选项**：等权 / 专家赋权 / 数据拟合
- **选择**：两级（2 : 1），只主张顺序不主张比例
- **理由**：样本不够做数据拟合。顺序的依据是「商业意图的明确程度」。
- **代价**：仍是先验。用敏感性分析（权重 ±20%、60/40 换成 50/50 和 70/30）证明排序对它不敏感。

### D-08 疑似档必须有行动引导

- **质疑**：测评区人人都提品牌，「品牌 + 推荐话术」会大面积误报。
- **选择**：必须出现行动引导（专属福利、限时、去哪买）；「品牌方提供样品」单列为披露
- **代价**：召回率下降。

### D-15 三档加区间

- **质疑**：0–100 分五档，精度装得太高。58 和 62 有什么区别？
- **选项**：单个分数五档 / 分数加区间三档 / 两个子分不合成
- **选择**：分数 + 区间 + 低中高三档
- **理由**：区间下界只算确证、上界把疑似全算上，直接回应「分数只是下界」这个局限。校准样本支撑不了五档的分辨率。
- **代价**：界面更复杂。

## 分类类

### D-09 关键词误判

- **质疑**：「这期不是恰饭」；专门讲广告行业的视频。
- **选择**：否定模式排除 + 有模型时复核；证据原文展示给用户自行判断
- **代价**：无模型时仍有误报，用实测精确率说明。

### D-10 大模型只分类、不出分，且影响有上界

- **质疑**：模型不稳定，同一个人跑两次分数不同。
- **选项**：模型直接打分 / 纯关键词 / 规则出分 + 模型分类
- **选择**：规则出分 + 模型分类。A、B 两档只由规则判定，模型只能影响 C 档。
- **理由**：模型直接打分不可复现，也说不出计算方式，与验收要求冲突。纯关键词对软广的召回低。现在的做法下，模型对总分的最大影响是可以算出来的。
- **配套**：temperature 0；按内容哈希缓存；每条证据标注来源是规则还是模型。
- **代价**：软广识别完全依赖模型；没有 API Key 时退化为关键词组合。

### D-11 提示注入

- **质疑**：视频简介是不可信输入，可以写「忽略以上指令」。
- **选择**：模型输出限定为枚举值；引用必须是原文子串，否则整条丢弃；加上 D-10 的影响上界
- **理由**：即使注入成功，最坏结果也只是 C 档误判，不会波及 A、B 档。

## 数据类

### D-12 置顶评论

- **质疑**：只看标题和简介；B 站的带货蓝链主要在置顶评论。
- **选择**：置顶评论列为必须验证的数据源，可行则必做
- **代价**：多一类请求，触发风控的风险上升。

### D-13 「未能检查」单列

- **质疑**：页面结构变了没抓到，和创作者确实没有，是两回事。
- **选择**：账号层指标三态（有 / 无 / 未能检查），未能检查只降置信度不扣分

### D-16 合规边界

- **选择**：只读用户浏览器里已经可见的公开内容；用户手动触发；单人规模；不上传、不持久化创作者数据；发给模型的只有公开文本，并在设置页明示。

### D-17 数据源可行性只能在真实浏览器里验证

- **事实**：2026-11-15 从命令行直接请求 `x/web-interface/view`，返回风控拦截页（非浏览器环境）。
- **结论**：这不能说明浏览器里不可用，只说明无法在开发环境里验证。
- **选择**：在插件里做一个「数据源自检」，在真实页面上逐项报告每个数据源是否可用；提取层为每项数据准备主、备两条路径。

## 验证类

### D-14 校准不依赖专业判断

- **质疑**：自己设计规则又自己标注，是循环论证。而且标注者不是领域专家。
- **选项**：自己凭感觉标 / 找第二人 / 改变验证方式
- **选择**：
  1. 只标可观察的事实（有没有购买链接、有没有广告声明），不标主观判断
  2. 用两组极端样本检验区分度，代替人工排序
  3. 模型作为第二标注者，只人工复核规则与模型不一致的条目
- **代价**：C 档无法验证；模型一致性不等于准确率；只能证明分得开两头。

## 工程类

### D-18 技术选型

- **选择**：Chrome MV3 + WXT + TypeScript + React + Vitest；侧边栏而非弹窗；npm
- **理由**：侧边栏 —— 用户点证据链接跳转时，弹窗会关闭，报告就没了。WXT —— 省去手写 manifest 和构建配置，时间只有 3–5 天。评分引擎独立成纯函数模块，可以脱离浏览器测试。
- **代价**：多一个构建依赖。

### D-19 先建仓库再写代码

- **理由**：提交历史本身就是过程证据，事后一次性上传会丢掉它。
